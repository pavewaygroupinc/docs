---
title: "Idempotency"
description: "Safely retry API requests without double-charging your customers or creating duplicate orders."
---

Pursar supports Stripe-standard idempotency on all mutating API endpoints (`POST` and `PATCH`). An idempotent request guarantees that performing the same operation multiple times produces the exact same outcome as performing it once, preventing duplicate charges when mobile connections drop or network timeouts occur.

---

## How It Works

To make an idempotent request, attach an `Idempotency-Key` header containing a unique string (typically a UUID v4):

```http
POST https://api.viarosandbox.com/v1/charges/mobile-money
Authorization: Basic base64(sk_test_...:)
Content-Type: application/json
Idempotency-Key: 9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d
```

```bash
curl -X POST https://api.viarosandbox.com/v1/charges/mobile-money \
  -u sk_test_live_secret_key_12345: \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: $(uuidgen)" \
  -d '{
    "amount": 25000,
    "currency": "XAF",
    "phone": "+237671234567",
    "customer_name": "Amara Diallo",
    "customer_email": "amara@example.com",
    "description": "Premium Service License #104",
    "merchant_reference": "ORD_2026_104"
  }'
```

### Execution Lifecycle

1. **First Attempt**: Pursar verifies the key, acquires an atomic lock on the key, executes the payment or creation logic, and saves the HTTP status code and response payload into the distributed cache.
2. **Subsequent Attempts**: If your application resends the identical request with the same `Idempotency-Key` (e.g. after a client-side network drop), Pursar intercepts the request and replays the cached response immediately, returning an `Idempotent-Replay: true` header. No second transaction is billed.
3. **Concurrent Collisions**: If a second request arrives while the first request is still being processed by the telecom network, Pursar safely returns an HTTP `409 Conflict` error indicating that an operation is currently in flight with this key.

---

## Error Handling & Key Mismatches

If you send a request with an `Idempotency-Key` that was previously used for a **different request body or different URL path**, Pursar rejects the request with an `idempotency_error`:

```json
{
  "error": {
    "type": "idempotency_error",
    "code": "idempotency_key_in_use",
    "message": "Keys for idempotent requests can only be used with the original request parameters they were first submitted with.",
    "param": "idempotency_key"
  }
}
```

## Best Practices

- **Generate UUIDs per Business Intent**: Generate a fresh UUID v4 for each unique business action (e.g. at the moment the customer taps "Pay"). Do not hardcode or generate keys based solely on timestamp.
- **TTL Window**: Pursar persists idempotency records for **24 hours**. After 24 hours, the key expires and can be reused.
- **Safe Automatic Retries**: In your SDK or client HTTP layer, configure automatic retries for transient HTTP errors (`408 Request Timeout`, `502 Bad Gateway`, `503 Service Unavailable`, `504 Gateway Timeout`) using the same idempotency key and exponential backoff.
